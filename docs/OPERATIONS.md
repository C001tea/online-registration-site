# Эксплуатация: деплой, мониторинг, резервные копии

## Сервер
- Oracle Cloud, Always Free **VM.Standard.A1.Flex** (4 OCPU, 24 ГБ, ARM/aarch64),
  Ubuntu 24.04, регион Frankfurt. IP `138.2.140.254` (Reserved, `salon-ip`).
- API: **https://api.timepoint.tech** (DNS-запись A `api` в Namecheap).
  Фронтенд ходит туда через прокси Vercel (`vercel.json` во фронтенде).
- Вход: `ssh -i <ключ> ubuntu@138.2.140.254`. В GitHub — секреты `NEW_SERVER_HOST`,

- Первая настройка машины: `deploy/setup-server.sh` (Actions → Setup new server).
- Изменить несекретную настройку в `.env` (например, `HTTPS_ONLY`):
  Actions → Server settings → Run workflow. Применяется деплоем без простоя.
- Переезд со старого сервера (`158.101.163.232`) выполнен 28.10.2026: workflow
  `new-server-rehearsal.yml` и `new-server-cutover.yml`. Старый сервер остановлен
  (web выключен), его база — запасная копия на время после переезда.

## Деплой
Автоматически при мёрже в `main` (`.github/workflows/deploy.yml`):
1. **Тесты** (`ci.yml`): `manage.py check`, проверка миграций, `manage.py test`.
   Если тесты красные — деплоя нет. Эти же тесты запускаются на каждый PR.
2. **Сервер, без простоя** (`deploy/deploy.sh`, «синий-зелёный» деплой):
   - `git pull`, сборка нового образа — старый контейнер продолжает работать;
   - миграции и `collectstatic` во временном контейнере — тоже пока работает старый;
     если они упали (ошибка в коде, миграции) — деплой останавливается, сайт
     остаётся на старой версии;
   - `caddy reload` (применяет изменения `deploy/Caddyfile`);
   - **новый** контейнер `web` запускается **рядом со старым**; Caddy распределяет
     запросы между ними;
   - скрипт ждёт, пока новый ответит на `/api/health/` (до 2 минут). Не ответил —
     новый удаляется, работает старый, workflow красный;
   - Caddy переключается **только на новый** контейнер (плавный `caddy reload`),
     и лишь потом старый плавно останавливается: дорабатывает начатые запросы (до 30 с).
     Без этого запросы продолжали приходить в останавливаемый контейнер, повисали
     на несколько секунд и обрывались — на продакшене по одному 502 за деплой
     (сервер в своп, процессы старого контейнера завершаются медленно);
   - в конце Caddy возвращается на имя сервиса `web` и выводит в лог ошибки прокси
     за время деплоя, память сервера и контейнеров.

Проверено на копии продакшена (Postgres + Django + Caddy в Docker), запросы каждые
0,2 с во время деплоя: переход со старой схемы — 158/158 ответов 200, повторный
деплой — 272/272, деплой с ошибкой в коде — старая версия продолжила работать (62/62).

Gunicorn запускается с `--preload`: порт открывается только когда Django уже
загружен. Без этого новый контейнер принимал запросы сразу, а отвечал через ~30 с
(пока воркеры грузят приложение) — на продакшене это давало 502. Пока порт закрыт,
Caddy отправляет запрос в старый контейнер. Проверено: при искусственно медленной
(+20 с) загрузке Django без `--preload` запросы висели 20,8 с, с ним — пауза не больше 0,5 с.

Посмотреть контейнеры: `docker compose ps web` (их имена теперь вида
`online-registration-site-web-2`, номер растёт с каждым деплоем). Логи:
`docker compose logs --tail 50 web`.

Миграции выполняются до переключения на новый код, поэтому они должны быть
совместимы со старым кодом (добавлять поля/таблицы — можно; удалять или
переименовывать — в два деплоя).

При обычном перезапуске сервера контейнер стартует как обычно. Ручной деплой:
`cd ~/online-registration-site && sh deploy/deploy.sh`.

## Мониторинг
- `GET /api/health/` → `{"status": "ok"}` (200), если приложение и база доступны,
  иначе 503.
- `.github/workflows/uptime.yml` каждые 15 минут проверяет сайт, API через Vercel
  и API напрямую. Если не отвечает (3 попытки с паузой 20 с) — workflow падает, и
  GitHub присылает письмо тому, кто последним менял этот файл (Actions → Uptime).
  Расписание GitHub не точное: проверка может запускаться реже, чем раз в 15 минут.

## Резервные копии базы
`.github/workflows/backup.yml` — ежедневно в 01:17 UTC и вручную (Actions → Backup →
Run workflow):
- копия на сервере: `~/backups/business_db-<дата>.dump`, хранятся последние 14;
- копия вне сервера: артефакт workflow `business_db-<дата>.dump.gpg`, хранится 30 дней,
  **зашифрован** (репозиторий публичный).

### Один раз настроить
1. Придумать длинный пароль для шифрования и **сохранить его в менеджере паролей** —
   без него копии не расшифровать.
2. GitHub → репозиторий → Settings → Secrets and variables → Actions →
   New repository secret: `BACKUP_PASSPHRASE` = этот пароль.
3. Actions → Backup → Run workflow — убедиться, что прошёл зелёным и появился артефакт.

### Восстановление
Копия с сервера (`~/backups/...dump`) или из GitHub (скачать артефакт, распаковать zip, затем
`gpg -d -o business_db.dump business_db-<дата>.dump.gpg` — спросит пароль).

```bash
cd ~/online-registration-site
docker compose stop web                      # чтобы никто не писал в базу
docker exec -i postgres_db pg_restore -U artacsercs -d business_db \
    --clean --if-exists --no-owner < /путь/к/business_db.dump
docker compose up -d web
curl -s https://api.timepoint.tech/api/health/
```
`--clean` заменяет текущие данные данными из копии. Чтобы сначала посмотреть копию,
не трогая рабочую базу, восстановите её в отдельную базу:
`docker exec postgres_db createdb -U artacsercs restore_check` и тот же `pg_restore`
с `-d restore_check` (потом `dropdb -U artacsercs restore_check`).

Процедура проверена на копии продакшена: удалили записи и мастеров →
восстановили из зашифрованной копии → все данные на месте.

## Telegram-бот (подтверждения и напоминания)
Код — приложение `notifications/`. Работает, только если задан `TELEGRAM_BOT_TOKEN`.
- **Токен**: секрет GitHub `TELEGRAM_BOT_TOKEN`; каждый деплой записывает его в `.env`
  на сервере. Сменить токен: обновить секрет и перезапустить последний Deploy Backend.
- **Вебхук** регистрируется при каждом деплое (`manage.py telegram_setup`):
  `https://api.timepoint.tech/api/telegram/webhook/`, подлинность — секретный заголовок.
- **Контейнер `telegram`** (`manage.py telegram_worker`): каждые 2 с отправляет очередь
  сообщений (таблица `OutgoingMessage`, повторы при сбоях Telegram), раз в минуту ставит
  напоминания: за 24 часа (с кнопками) и за 1 час. Логи: `docker compose logs telegram`.
- **Клиент**: после записи на сайте — кнопка «Подтвердить в Telegram» (ссылка `t.me/<бот>?start=a_…`),
  в боте кнопки «Подтверждаю» / «Отменить». Клиент с аккаунтом подключает Telegram один раз.
- **Салон**: владелец, админы и мастер записи подключают Telegram в панели
  (меню → «Уведомления в Telegram») и получают новые записи и отмены клиентами.
  Клиенту приходит сообщение, если салон отменил или перенёс запись.
- Отправленные сообщения хранятся 30 дней.

## Финансы (панель салона → «Финансы»)
Приложение `finance/`. Отчёты, касса и зарплаты — только владелец; оплату визита
принимают владелец и админ; мастер видит «Моя зарплата».
- **Оплата визита** (кнопка «Оплата» в карточке записи): цена услуги − скидка, способ —
  наличные/карта/перевод; визит становится «Пришёл». Оплаченный визит нельзя
  перенести или сменить статус — владелец сначала отменяет оплату.
- **Отчёт за период**: выручка, средний чек, скидки, расходы (в т.ч. зарплаты), прибыль;
  по способам оплаты, мастерам, дням; визиты «Пришёл» без оплаты отмечены отдельно.
- **Касса за день**: наличные на начало дня (нарастающим итогом), приход, расход, на конец;
  приходы и расходы вне визитов (аренда, материалы…) добавляются вручную.
- **Зарплаты**: схема мастера — % от оплаченных визитов (после скидки) + фикс за день,
  в который был хотя бы один оплаченный визит. Выплата за период проводится расходом
  по кассе (категория «Зарплата»), отменяется только в «Зарплатах».

## Фото салона и мастеров
Загружаются в панели: «Настройки» (логотип, главное фото) и «Мастера» (фото мастера).
Хранятся в Cloudinary (ключи `API_KEY_CLOUDINARY`, `API_SECRET_CLOUDINARY` в `.env`;
деплой пишет в лог, заданы ли они). Браузер уменьшает фото перед отправкой, сервер
проверяет формат (JPG/PNG/WebP, до 10 МБ), ещё раз уменьшает (главное фото — 1600 px,
мастер — 800, логотип — 600) и удаляет метаданные (EXIF, в т.ч. геолокацию).
Старый файл удаляется из Cloudinary после замены. Менять фото могут владелец и админ.
## Клиентская база (панель → «Клиенты»)
Владелец и админ. Клиент — номер телефона из записей салона (аккаунт на сайте не нужен):
визиты, неявки, отмены, сколько оплатил, средний чек, последний и следующий визит,
любимый мастер и услуга, история записей. Заметка о клиенте (`dashboard.ClientNote`)
видна только персоналу салона. «Записать снова» открывает в журнале форму с телефоном
и именем клиента; из карточки записи в журнале есть ссылка «Карточка клиента».
