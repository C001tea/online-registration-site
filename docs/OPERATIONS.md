# Эксплуатация: деплой, мониторинг, резервные копии

## Деплой
Автоматически при мёрже в `main` (`.github/workflows/deploy.yml`):
1. **Тесты** (`ci.yml`): `manage.py check`, проверка миграций, `manage.py test`.
   Если тесты красные — деплоя нет. Эти же тесты запускаются на каждый PR.
2. **Сервер, без простоя** (`deploy/deploy.sh`, «синий-зелёный» деплой):
   - `git pull`, сборка нового образа — старый контейнер продолжает работать;
   - миграции и `collectstatic` во временном контейнере — тоже пока работает старый;
     если они упали (ошибка в коде, миграции) — деплой останавливается, сайт
     остаётся на старой версии;
   - `caddy reload` (применяет изменения `deploy/Caddyfile`);
   - **новый** контейнер `web` запускается **рядом со старым**; Caddy распределяет
     запросы между ними;
   - скрипт ждёт, пока новый ответит на `/api/health/` (до 2 минут). Не ответил —
     новый удаляется, работает старый, workflow красный;
   - старый контейнер плавно останавливается: дорабатывает начатые запросы (до 30 с).

Проверено на копии продакшена (Postgres + Django + Caddy в Docker), запросы каждые
0,2 с во время деплоя: переход со старой схемы — 158/158 ответов 200, повторный
деплой — 272/272, деплой с ошибкой в коде — старая версия продолжила работать (62/62).

Gunicorn запускается с `--preload`: порт открывается только когда Django уже
загружен. Без этого новый контейнер принимал запросы сразу, а отвечал через ~30 с
(пока воркеры грузят приложение) — на продакшене это давало 502. Пока порт закрыт,
Caddy отправляет запрос в старый контейнер. Проверено: при искусственно медленной
(+20 с) загрузке Django без `--preload` запросы висели 20,8 с, с ним — пауза не больше 0,5 с.

Посмотреть контейнеры: `docker compose ps web` (их имена теперь вида
`online-registration-site-web-2`, номер растёт с каждым деплоем). Логи:
`docker compose logs --tail 50 web`.

Миграции выполняются до переключения на новый код, поэтому они должны быть
совместимы со старым кодом (добавлять поля/таблицы — можно; удалять или
переименовывать — в два деплоя).

При обычном перезапуске сервера контейнер стартует как обычно. Ручной деплой:
`cd ~/online-registration-site && sh deploy/deploy.sh`.

## Мониторинг
- `GET /api/health/` → `{"status": "ok"}` (200), если приложение и база доступны,
  иначе 503.
- `.github/workflows/uptime.yml` каждые 15 минут проверяет сайт, API через Vercel
  и API напрямую. Если не отвечает (3 попытки с паузой 20 с) — workflow падает, и
  GitHub присылает письмо тому, кто последним менял этот файл (Actions → Uptime).
  Расписание GitHub не точное: проверка может запускаться реже, чем раз в 15 минут.

## Резервные копии базы
`.github/workflows/backup.yml` — ежедневно в 01:17 UTC и вручную (Actions → Backup →
Run workflow):
- копия на сервере: `~/backups/business_db-<дата>.dump`, хранятся последние 14;
- копия вне сервера: артефакт workflow `business_db-<дата>.dump.gpg`, хранится 30 дней,
  **зашифрован** (репозиторий публичный).

### Один раз настроить
1. Придумать длинный пароль для шифрования и **сохранить его в менеджере паролей** —
   без него копии не расшифровать.
2. GitHub → репозиторий → Settings → Secrets and variables → Actions →
   New repository secret: `BACKUP_PASSPHRASE` = этот пароль.
3. Actions → Backup → Run workflow — убедиться, что прошёл зелёным и появился артефакт.

### Восстановление
Копия с сервера (`~/backups/...dump`) или из GitHub (скачать артефакт, распаковать zip, затем
`gpg -d -o business_db.dump business_db-<дата>.dump.gpg` — спросит пароль).

```bash
cd ~/online-registration-site
docker compose stop web                      # чтобы никто не писал в базу
docker exec -i postgres_db pg_restore -U artacsercs -d business_db \
    --clean --if-exists --no-owner < /путь/к/business_db.dump
docker compose up -d web
curl -s https://158-101-163-232.sslip.io/api/health/
```
`--clean` заменяет текущие данные данными из копии. Чтобы сначала посмотреть копию,
не трогая рабочую базу, восстановите её в отдельную базу:
`docker exec postgres_db createdb -U artacsercs restore_check` и тот же `pg_restore`
с `-d restore_check` (потом `dropdb -U artacsercs restore_check`).

Процедура проверена на копии продакшена: удалили записи и мастеров →
восстановили из зашифрованной копии → все данные на месте.
